## Where it is

**Windows.** The game boots, plays its intro screens, loads, goes through its first-use menus (language, screen adjustment, brightness, drawn by its own shaders in its bronze font) and plays the opening cinematic, `OPENINGINT6.M2V`, with picture and sound in sync: the video decodes at 29.98 fps for the whole movie. The menus answer the controller and the keyboard. After the cinematic the main menu draws its scene at ~30 fps (12-15 before the 2026-10-18 SPU/RSX work); it renders correctly except for the amber slabs' interior glow and its bloom (see Next). From the main menu, X four times starts the game: the loading movies play while the first level loads, and the game enters the level (Kratos chained, ~31 fps; reached 2026-10-18 with `SPU_REJOIN`/`SPU_REJOIN_CALL`, see Next). The level still shows texture and lighting faults and needs performance work. The first-use menus run at 45-90 fps, the main loop at ~35 Hz during the cinematic; a panel in the top-right corner shows FPS, frame time, speed, CPU and GPU. Every SPU job module now runs lifted. The launcher (`launcher/`, `scripts/launcher.ps1`) sets the window, language, subtitles and mods, and the game renders inside its window.

**macOS.** The intro screens drew through Metal on the first lift; the Mac build needs the re-lift with ps3recomp's v0.15 lifter to catch up. The v2 RPCS3 renderer is Windows-only for now (MSVC); a Mac build leaves `ASCENSION_RPCS3_RSX` off and keeps live draw's Metal path.

There is no release.

1. **The first level (reached 2026-10-18).** The game now goes from the main menu through the loading movies into the first level (Kratos chained, ~31 fps), `SPU_REJOIN=204:9700-1C000` and `SPU_REJOIN_CALL=1` are defaults now (movies at full speed, smooth audio); without them the level loads too, the movies at ~64% with stuttering audio.
   - **What froze the level load:** the particle job's next phase (the mechanism in Debugging log, `0x983100`) lost one of its five tasks now and then, so the PPU main thread waited in `func_003A5D00` for `[0x983168]` (4) to reach `[0x98317C]` (5) for good. The runtime's minimal taskset scheduler (`spu_workload.c`, `ts_start_ready`/`spu_taskset_task_exited`) cleared ready/pending/enabled bits with a plain byte read-modify-write, while the SPU task library creates the next phase's tasks with GETLLAR/PUTLLC on the same line: an exit landing on a creation in the same byte wrote the old byte back and dropped the new task. The clears now hold the lock-line lock and break the line's reservations (`ts_bits_clear`), as `spurs_bitset_rmw` already did for the signal bits. Faster SPU code (the rejoin) made the race likelier, which is why the freeze point moved from run to run. Found with `SPU_ATOM_EA=983100` (`SPU_ATOM_EA_MAX=0`) and `SPURS_TASKSET_TRACE=1`: image 3 (lr `0xBAA8`/`0xBAC0`) claims items on `+0x64`, image 1 (lr `0xE498`) counts them done on `+0x68`, five `[taskset] run image=1` per round except the last.
   - **Also new (ps3recomp, uncommitted):** `SPU_REJOIN_CALL=1`: lifted code the interpreter rejoins runs in a drain of its own (`spu_drain_interp`) whose host return resumes interpretation at the right pc (it was not the cause of the freeze, but it is the correct return path); `SPU_PCWATCH_R90=1` (job registers and the `r90+0x220` block at `SPU_PCWATCH` hits).
   - **Level performance (2026-10-18):** 14 -> 16 fps. Module 218's (`jobmod_7868e9b847d1`, the old "209") streamed fragments `0x723300` and `0x725EA0` sat inside two `seen: false` spans of `tools/job_fragments.json` (`0x722da0`, `0x725490`), so nothing recognised them and they ran interpreted (1.23G SPU instructions a run, now 51M); both spans are split at their real fragment starts. Stores in the lifted PPU code are inline now (patch 0038); the PPU thread no longer shows `vm_write64`, but the frame is SPU-bound.

## How it is built

The layout is `ascension-recomp/{ps3recomp, ascension, work}`; `ps3recomp` is the fork's branch `ascension-v0.15`, or v0.15.0 with `patches/` applied.

| Step | State |
| --- | --- |
| Disc identity | `BCES-01741`, *God of War: Ascension (EU)*, 1.00, firmware 4.31. The image keeps the disc's region table but its sectors are already decrypted. Extract it into `work/disc` (so that `work/disc/PS3_GAME/USRDIR` exists). |
| `EBOOT.BIN` | 8,586,688 bytes, SHA-256 `0ecbc9c0cd0bf4a493611148e7d7d4a3ba48d7948ecb7969c6e735fca9bb0b9f`, a SELF (version 2, key revision `0x001C`). |
| `EBOOT.BIN` → `EBOOT.ELF` | With RPCS3 (*Utilities › Decrypt PS3 Binaries*, the console firmware installed) or `python tools/decrypt_self.py EBOOT.BIN -o EBOOT.ELF --keys <scetool keys file>`: 8,584,256 bytes, SHA-256 `93d94d54ba5dd76ed2d6c86b6558f4f8d2e02355604abca26e0bb71267943be5`. ELF64, big-endian, PowerPC 64, entry OPD `0x808360` (code `0x10410`), TOC `0x81EF60`, no section headers. Put it beside `EBOOT.BIN`. |
| Imports / NIDs | 345 imports from 25 libraries; 308 resolve to a name. About 243 of them are named somewhere in ps3recomp's libraries (an upper bound on what is implemented). |
| Function boundaries | 19,199 functions (`find_functions.py`), every `.opd` descriptor a function start; 7,556 OPD entries. Code ends at `0x62C4CC`, right after the import stubs (`0x627954`-`0x62C494`). |
| SPU images | 4 embedded (176 KB, `extract_spu_images.py`) plus the `Wws_Job` policy module (`tools/extract_spu_pm.py`), lifted and registered by fingerprint (`build_spu_workloads.py`). The policy module is re-lifted with extra entries: `build_spu_workloads.py ... --relift --extra-funcs spu_wws_pm_at_0077CA80=0xA2C,0xA68,0x3368,0x3378`. |
| PPU lifting | With the v0.15 lifter (an older one corrupts the game's heap): 19,570 functions, 1.8 million lines of C++ (126 MB) in 12 units of 150,000 lines (each fits a 16 GB machine), 62 jump tables, 676 mid-function entries, 345 import stubs as HLE calls. `python ps3recomp/tools/ppu_lifter.py work/input/EBOOT.elf --functions meta/functions.json --hle-stubs meta/EBOOT.imports.json --toc 0x81EF60 --code-end 0x62C4CC --chunk-lines 150000 -o src/recomp`; under a minute. |
| SPU job modules | The 15 Wws modules the job manager streams from the EBOOT (`0x6B2480`-`0x82B780`), dumped with `SPU_DUMP_OVL=<dir>,0x4000` and lifted with `scripts\windows\relift.ps1 jobmods` (`lift_jobmods.py --extra-funcs-json tools/jobmods_extra_funcs.json`, images 200-214). Module 209's streamed code fragments are lifted position-independently with `scripts\windows\relift.ps1 fragments` (`tools/job_fragments.json`, images 300-333). |
| Build | `AscensionRecomp.exe`, ~89 MB: CMake and Ninja; on Windows clang-cl from Visual Studio 2022 (`scripts\windows\build.ps1`), on macOS Apple clang (`scripts/mac/build.sh`) with `brew install cmake ninja sdl2 glslang spirv-cross ffmpeg`. Configured with `-DPS3RECOMP_FFMPEG_RUNTIME=ON` (and on Windows `-DPS3RECOMP_FFMPEG_INCLUDE_DIR=<work/deps/ffmpeg-9.0.2-include>`, with `avcodec-63.dll`, `avutil-61.dll` and `swresample-7.dll` beside the executable) so `cellVdec` decodes the MPEG-2 cinematic. Python tools need 3.10 or newer. 20-40 minutes from scratch, 16 GB of memory. The link writes `AscensionRecomp.map`, which names the addresses the sampling profiler prints (`PS3_DEBUG=<file>`, command `prof <tid> <s>`). |
| Running | The launcher (`scripts\windows\launcher.ps1`, `scripts/mac/launcher.sh`), or `build\win\AscensionRecomp.exe ..\work\disc\PS3_GAME\USRDIR\EBOOT.ELF`; for test runs `scripts\windows\run.ps1` (see `scripts/README.md`). On macOS `scripts/mac/run.sh` mounts the disc image in `work/disc` and opens a window (the first time, `ASCENSION_ISO=<path to the .iso>`). Saves go to `gamedata/dev_hdd0`. |

## Runtime switches

Set before `main` by `host/ascension_defaults.cpp` (an environment value already set wins):

| Switch | Why |
| --- | --- |
| `PS3_EDGE_ZLIB_HLE=1` | Edge Zlib inflates on the host; without it the archives never load. |
| `RSX_LIVE_DRAW=1` | The live NV4097 draw engine; the default D3D12 path records none of this title's draws. |
| `GCM_PARK_WAIT_MS=2000` | A parked FIFO waits for the SPU jobs to patch it. |
| `GCM_SEMA_ACQUIRE=1` | A FIFO `SEMAPHORE_ACQUIRE` really waits (for the post-process tasks' label). |
| `GCM_PARK_SPU_HOLD_MS=1000` | A patched park waits while SPURS tasks run (the first frame has no ACQUIRE). |
| `GCM_REPORT_SPU_HOLD_MS=50` | A GET_REPORT waits while the post-process tasks are in a round, so RsxSync's next signal is not eaten. |
| `SPURS_READY_LEVEL=1` | readyCount is a level, as the real kernel treats it. |
| `SPU_REJOIN=204:9700-1C000`, `SPU_REJOIN_CALL=1` | Job module 204 (the level-load job) runs lifted, not interpreted: the loading movies play at full speed with smooth audio. The level loads without them too, at 50-75% speed. |
| `LD_PERF_OVERLAY=1`, `PS3_VERBOSE=0` | The performance panel; per-frame log lines off. |

Set by the launcher: `PS3_PARENT_HWND` (render inside its window), `PS3_WINDOW_SIZE`, `PS3_FULLSCREEN`, `PS3_WINDOW_ICON`, `PS3_ESC_QUITS`, `PS3_SYS_LANG`, `PS3_ENTER_BUTTON`, `PS3_MODS`, the renderer and video switches (`PS3_RSX`, `PS3_RSX_RENDERER`, `PS3_RENDER_SCALE`, `PS3_ASPECT`, `PS3_SCALE_FILTER`, `PS3_VSYNC`, `PS3_ANISO`) and the controls (`PS3_KEYMAP`, `PS3_PADMAP`, `PS3_PAD_DEADZONE`); see `launcher/README.md`.

## The game's own data

- **Language archives:** `ENGLISH`, `FRENCH`, `GERMAN`, `GREEK`, `ITALIAN`, `POLISH`, `PORTUGUESE`, `RUSSIAN`, `SPANISH`, `TURKISH` (`.PSARC`, and `MP-` ones for multiplayer). The game picks one from the console language (`cellSysutilGetSystemParamInt`), and asks for Greek itself at the first start.
- **System save** `BCES01741-SYSDATA/SAVEDATA` (4 KB, no checksum): a 16-byte header, then the options block the boot hands out (`func_0001A680`): `+0x0C` text language (`func_003963A8`), `+0x0D` voice language (`func_00396348`), `+0x0E`-`+0x16` volumes and screen settings, `+0x18` subtitles (`func_00032C74`). Written at the first start from the console language: English gives text 18 (English UK) and voices 1; Portuguese gives 7 and 7. The launcher writes these bytes (file offsets `0x1C`, `0x1D`, `0x28`) before each start, since the game no longer asks the console afterwards.
- **Language table:** `GAME.PSARC: /WAD/PS3_BE/LANGS_<title id>.TXT`, one per release, `<console code> <locale> <archive name>` per line (BCES01741: 2 fr, 3 es, 4 de, 5 it, 6 nl, 7 pt, 8 ru, 16 pl, 18 en-gb, 19 tr, 20 el; BCUS98232: 1 en, 2 fr, 17 pt-br, 21 es-la). The locale names the text (`RESOURCES.PSARC: R_LANG_<LOCALE>.WAD`, all fifteen on both discs), the archive name the voices (`<NAME>.PSARC`, `MP-<NAME>.PSARC`); `LOCALIZED_ARCHIVES` lists those archives. A code the table lacks falls back (17 gives Portugal's Portuguese). The PT-BR mod (`tools/make_ptbr_mod.py`, `tools/psarc_replace.py`) adds `17 pt-br BR_PORTUGUESE` to `LANGS_BCES01741.TXT`, the US disc's `BR_PORTUGUESE.PSARC`/`MP-BR_PORTUGUESE.PSARC` as they are, and both to `LOCALIZED_ARCHIVES`; the game then writes 17/17 in its save. The two discs' big archives are byte-identical in size; `GAME.PSARC` differs by 206 bytes.
- **Options in memory:** `0x842D18`; `+0x3D` (`0x842D55`) is the subtitle switch.
- **Command line:** `-bootSelect`, `-subtitlesOn` and `-extraVRAM` set bytes `0x97D348`-`0x97D34A`; `-subtitlesOn` only changes the default the save then overrides. `PS3_ARGV` passes arguments.

## ps3recomp changes

On the branch [`ascension-v0.15` of the fork `arnaldolima1/ps3recomp`](https://github.com/arnaldolima1/ps3recomp/tree/ascension-v0.15), commits on ps3recomp v0.15.0, also kept here as `patches/` (0001-0037). Upstream fixed the `sys_lwcond_t` layout, files past 2 GB, `cellGcmMapEaIoAddressWithFlags`, the SPU microstep and interpreter hand-back, parked FIFOs and GET_REPORT into main memory on its own (#248, #256, #266, #268, #277, #312), so the rebase took its versions. The older branch `ascension` (on v0.14.0) is kept as it was. By area:

- **SPURS:** the second generation (`cellSpursInitializeWithAttribute2`, `cellSpursCreateTaskset2`/`Task2`/`JoinTask2`, their attribute initializers, `cellSpursAttributeEnableSystemWorkload`); 32 workloads and flags1, ported onto v0.15.0's per-SPU scheduler; the kernel's tempArea filled at every selection; `SPURS_READY_LEVEL`; `_cellSpursLFQueuePushBody`; tasksets (one start per created task, `CellSpursTaskset2` at 0x2900 bytes with its two event flags, SPU-created tasks started); the taskset bitsets updated under the lock-line lock; the kernel woken by GPU reports (`spurs_external_event`, `SPURS_IDLE_BACKOFF_MAX`); task waits that re-check their signal every 2 ms (`SPU_WAITSIG_POLL_MS`).
- **SPU code:** position-independent lifts (`spu_lifter --pic`, `tools/lift_spu_pic.py`, `spu_overlay_register_pic`, eight `resident_code` slots with LRU replacement); the interpreter rejoining lifted code (`SPU_PROBE`, a per-image function bitmap) and honouring the interrupt-enable bits of conditional `bi*`; SSE4.1 forms of the float, select, shift and compare ops and `-msse4.1` for lifted SPU code; `lift_jobmods.py --extra-funcs-json`; `SPU_SHADOW` (compares a lifted function with the interpreter, run by run).
- **GCM and the FIFO:** the offset tables written through; `GCM_PARK_WAIT_MS` and a park's own grace over the stuck-get rule; a blocked `SEMAPHORE_ACQUIRE` exempt from it; `GCM_FLIP_PACE_MS` (off); `GCM_PARK_SPU_HOLD_MS` (parks recognised by address too); `GCM_REPORT_SPU_HOLD_MS` (QPC-timed, the walker kicked when the last task waits again); the vblank on the QPC clock at 59.94 Hz with one handler call per vblank.
- **Video, audio and the window:** live draw's X16 textures, framebuffer sRGB and texture gamma, fragment `DDX`/`DDY`; `cellVdecQueryAttrEx`/`OpenEx`, numbered timestamps for AUs without PTS, `CellVdecMpeg2Info`'s sequence fields, AUs held (not refused) while the picture queue is full; the performance panel (`LD_PERF_OVERLAY`); the host window (`rsx_host_window.h`: embedding, size, full screen, icon, Escape); the macOS window fix and numbered Metal frame dumps.
- **System:** Edge Zlib on the host (truncated output, the skip offset); `cellGamePatchCheck`; the console language and confirm button (`PS3_SYS_LANG`, `PS3_ENTER_BUTTON`); a mod overlay on USRDIR (`PS3_MODS`); the keyboard while a launcher window is in front; per-frame log lines behind `PS3_VERBOSE`.
- **Diagnostics:** `SPURS_KICKLOG`, `SPURS_WLDUMP`, `SPURS_PM_RUNLOG`, `SPURS_PM_TRACE`, `SPU_PCWATCH`, `SPU_LLAR0_TRAP`, `SPU_EVLOG`, `SPU_JOBAPI_LOG`, `SPU_COMMIT_EA`, `SPU_MFCLOG_IMG`/`_EA`/`_BYTES`/`_LSA`, `SPU_WAITSIG_EXITLOG`, `SPU_WAITSIG_MISSLOG`, `SPU_ITRACE_*`, `SPU_SMC_LSDUMP`, `SPU_PIC_LOG`, `SPU_INTERP_HIST`, `SPU_NOLIFT`, `SPU_JOB_HIST`, `SPU_TASK_TIMELOG`, `SPU_IRQ_DELIVER`, `LWCOND_TRACE`, `GCM_REPORTLOG`, `GCM_SEMALOG`, `GCM_REPORTFF`, `GCM_HOLD_LOG`, `VDEC_TIMELOG`, `PS3_HLE_HIST`, `LV2_SYSCALL_HIST`, `WATCHDOG_REGS`/`_DUMP`/`_UNWIND`, `LD_ZPROBE`, `LD_DEPTH_EQUAL_LEQUAL`, `HLE_BT_NID`, `t=` stamps on `[atom-ea]`/`[ww]`/`[GET_REPORT]`; `[null-read]` capped per reading function, with its registers.

## Debugging log

What each step found, newest first. Addresses are the game's (EU 1.00).

- **Main menu 1 -> 12 fps** (2026-10-17, Windows). The menu's frame waited on a job list (`0x11A9B880`, wid 3, `Wws_Job/CollisL`) whose 16 jobs per frame run on one SPU by design (`maxContention` 1); each took 80-230 ms because its code ran interpreted. Three layers: (1) module 207 brings its code as heap copies of header + fragments and as long stretches of the executable, which the GET-side tracking missed: fragments are now also found inside bigger GETs and by content at the interpreter (patch 0031), and the three stretches (`0x6AF1B0`, `0x6D66B0`, `0x716730`) are lifted whole; (2) eight resident code slots were too few for a block of a dozen fragments (now 32); (3) the job itself was a module the loading never streams (`0x6F4580`, entry `0x41E8`): `SPU_INTERP_HIST` showed 110M interpreted steps per 5 s at LS `0x80EC`, image 5 with no overlay. The executable holds 33 job modules (header: four `ila`, entry, size, ..., `C0DEC0DE` at `+0x20`); only 15 had been dumped. All 33 are now extracted from the executable and lifted (images 200-232).
- **Mods: recipes and included mods** (2026-10-17). The launcher lists `mods-builtin/` (no game files) with the user's mods; `psarc_patches` in a `mod.json` change files inside an archive, merged from all enabled mods into one generated archive at PLAY. Skip intro empties `/INTRO/BOOT_BCES01741.TXT` (normally `10,11,4,15`). The game lets START skip the opening cinematic from the second start on, not on the very first; `-skipintro` (a developer switch, byte `0x8A9989`) skips the intro and the movie but leaves the game stuck.
- **The launcher; language and subtitles in the system save** (2026-10-17, Windows). The game asks the console language only when it makes `BCES01741-SYSDATA`; later starts read their copy (`SAVEDATA` `0x1C`/`0x1D`), and the subtitle switch is `0x28`, handed to `func_00032C74` at boot (seen with `PPU_WWATCH=842D55`). The launcher writes them before each start.   - **Job lists.** A Wws job list is a workload header: `+0x08` the active array, `+0x20 + 4a` its capacity, `+0x3C` the job array (header + 0x80), and per array a row at `+0x40 + 16a`: `u16` jobs published, `u16` jobs taken, six `u16` per-SPU `minActive` (0xFFFF: idle). Entries are 8 bytes, `[type | loadCommandsSize << 8, EA]`, with the types in the order the game's disassembler names them: 0 `kNoJobYet`, 1 `kJobExists`, 2 `kGeneralBarrier` (the EA is a dependency), 3 `kNopJob`, 4 `kSetNextActiveArray`, 5 `kRsxBarrier`. The policy module takes every entry that is no longer `kNoJobYet`.
  - **Dependencies** are words `{u16 counter, u8 workloadId, u8 readyCount}`; the decrement that reaches zero sets that workload's readyCount (and leaves `0x0000FF00`).
  - **Per frame f** (`0x99AAA0` holds f) the PPU (`func_003E7230`) arms `0x99AAA4 = {5, EDGE_f}` (MeshProc's five jobs), `0x99AAB0 + 4i` and `0x99AAC0 + 4i = {1, ...}`, and `0x99AA84 + 4(f-1) = {6, EDGE_(f+1)}`. That last one takes one decrement from RsxSync's `kRsxBarrier` (job module code at LS `0x4618`, wid 18) and five that MeshProc's jobs request through the job API (`0x99AAA8`, copied into the job's parameters at `+0x68`; done by the policy module at LS `0x3218`).
  - **The break.** MeshProc's requested decrements are carried out when a job leaves the store stage, and the Wws pipeline (load, run, store) only advances when new jobs arrive: frame f's five land during frame f+1, when they land at all (in some runs `0x3218` never runs). Frame 3's EDGE list (EDGE0) then waits on `0x99AA88` at 5, never releases the slot `0x99AAC0`, and frame 5 never starts.
  - **The whole per-frame chain** (`SPU_ATOM_EA` with commit verdicts, `SPU_JOBAPI_LOG`, `GCM_REPORTLOG`): the GPU writes frame f's report (`0x1ED10 + 0x10n`) -> RsxSync (wid 18) passes its `kRsxBarrier` and decrements `0x99AA84 + 4f` once, then signals the five tasks of taskset `0x11027280` (registry image 2, which is `spu_0001_at_0067F580` -- the image names are ELF file offsets, the task is created at EA `0x68F580` with `cellSpursCreateTask2`; the barrier job module `0x77C180` sets their bits at LS `0x4A08`) -> the tasks work, signal one another and decrement the same dependency five times, once each (the task's own dependency decrement at LS `0x3150`, called from `0x37EC`; `0x3218` is inside it, not the job manager's) -> it reaches zero and wakes the next frame's EDGE list. The latency of one frame is the GPU's, and by design.

The walker now gets one segment further (reports up to `0x1ED70`, reference 5).

Next: what decides which dependency each task decrements (image 2's task code, its argument at `0x0FEFF5C0`).

What differs is the work per round: in frame 3 RsxSync signals the tasks twice and they complete `0x99AA84`; in frame 4 once, and two of them decrement `0x99AA88`. A task decrements its round's dependency once, when its count of outstanding items (word 3 of its frame at `$sp + 0x50`) reaches zero (LS `0x3740`); until then it goes back to waiting for more items. So the three tasks that miss `0x99AA88` are waiting for items that do not come, and those arrive with RsxSync's signals, which follow the GPU reports. ## Found so far

- **Edge Zlib:** the queue the first SPU task serves is Edge's zlib inflate queue (`edgezlib_inflate_queue.cpp`, the game's own assert names it). Its request has the layout the Twisted Metal port mapped (+0x00 destination, +0x0C source, +0x10 compressed size, +0x14 in-place buffer, +0x18/+0x24 output size, +0x28 busy), and the queue element carries the same. Inflating on the host, as that port does, unblocks the boot.
- **The `Wws_Job` policy module** is raw SPU code in the executable (12288 bytes at `0x77CA80`, FNV-1a-64 `0xC8D774963A96DCF2`). `tools/extract_spu_pm.py` extracts it and wraps it as an SPU ELF at LS `0xA00` into `meta/spu/`; `build_spu_workloads.py` then lifts it (194 functions) and registers it under that fingerprint, and all fifteen workloads resolve.

- **`sys_lwcond_t` layout (ps3recomp bug):** the runtime wrote the lwmutex as a 64-bit EA at +0x00 and the queue id at +0x08; the PS3 structure is 8 bytes (be32 lwmutex, be32 id). The game reads the first word before waiting, found 0 and never waited, so its FIOS threads deadlocked and no file was opened. Fixed on the fork.
- **Files past 2 GB (ps3recomp bug, Windows):** `cellFsLseek`, `cellFsFstat` and `cellFsStat` used `long` and `struct stat`, 32 bits on Windows. `RESOURCES.PSARC` (2.1 GB) failed to mount with -139 and the init gave up. Fixed with 64-bit helpers.
- **`_cellSpursLFQueuePushBody`** was missing: the PPU's first message to its SPU task never arrived. Implemented on the ring model ps3recomp derived from another title's consumer, under the lock-line lock; the message arrives and wakes the task, but the model does not match this game's consumer (see Next).
- **How the init failure was found:** a temporary `fprintf` after every call in the lifted `func_002AC3D8` (generated code, not kept) showed the archive-mount call returning -139 on the fourth archive.

- **Edge Zlib streaming:** the queue element has an output skip at +0x24 (also the low half of +0x18). The intro loader reads a compressed WAD as a 64-byte chunk header, then its payload, then the next header, each time inflating the same stream and skipping what it already has. Ignored, the first header (`DC_WAD_R_FX`) came back forever, the loader freed its buffers through the wrong heap (`Ice::Render::UnmapMainMemory` on addresses it never mapped, the renderer's memory table driven to -1) and the GCM IO mapping was destroyed: that was the old "iooffset == -1 / MemTable entry not found" stop.
- **GCM offset tables:** `cellGcmGetOffsetTable` gives the game a guest copy that map/unmap never updated. Now written through.
- **WWS interrupt handler:** the job manager acknowledges a DMA list stall from an SPU interrupt whose handler (LS `0xA2C`) builds a register-save stub at `0x3FEC0` at run time. Two runtime bugs killed it: the SMC microstep computed `lqa`/`stqa` addresses as `I16 << 4` (the stub came from the wrong template), and after handing an instruction to the interpreter it did not dispatch back into lifted code, so the policy module quit. The jobs then ran into `dfs` and other ops the interpreter lacked.

- **SPURS2 has 32 workloads.** The runtime stopped at 16, so `EDGE1`, `EDGE2` and `RsxSync` (wid 16-18) were never added. The frame-slot counters at `0x99AAC0` (released by the frame-end job) stayed at 1 and the render thread waited forever. Fixed: the second set of instance fields is used for wid 16-31.

- **SPURS2 flags and the second info table.** The barrier module reads flags1 (instance `+0x74`, copied to LS `0x174`) and needs `SF1_32_WORKLOADS` (0x40) before it looks up a wid >= 16; it computes that wid's info at `spurs + 0x1000 + 32*(wid-16)`. Without the flag it read its lock line from EA 0 and waited forever. Fixed.
- **The SPURS kernel's tempArea (ps3recomp gap).** The kernel copies the first 128 bytes of the CellSpurs instance into LS `0x100` at every workload selection; the runtime never did. The Wws barrier job module (`0x77C180`, id `0x43AF3402`, loaded at LS `0x4000`) reads flags1 there (`0x174`) before it looks a wid >= 16 up in wklInfo2: with the area empty it took its error path and spun on a GETLLAR of EA 0, and the frame's EDGE list never finished, at a different frame from run to run (`SPU_LLAR0_TRAP` caught it: registers, the last MFC commands, LS). Filled on every entry and poll now; the stall is deterministic since.
- **cellSpursModulePoll's answer.** The kernel answers with the selected workload in the high word; the runtime answered 0, which tells every policy module but wid 0's to yield after one poll. Kept as it was by default (a module that never yields would hold its host worker); `SPURS_READY_LEVEL=1` answers with a real selection.

- **GET_REPORT in main memory.** The game points the report DMA at the host buffer (`0xFEED0001`), so reports land at IO offsets in main memory; the runtime only kept them in a host array. Now written to guest memory too.

- **The black window was the renderer.** ps3recomp's default D3D12 path recorded none of this title's draws: every present had `draws=0`. The live NV4097 engine (`RSX_LIVE_DRAW`) executes them (thousands of draw groups, none dropped) and the intro screens come out right. `host/ascension_defaults.cpp` turns it on, with `PS3_EDGE_ZLIB_HLE`, before `main` (through the OS environment: the harness caches `getenv` misses). `LD_FRAME_DUMP=<dir>` writes the presented frame as `.ppm`.
